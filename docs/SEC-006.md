# SEC-006 — implementation awaiting independent verification

This branch depends on SEC-005. No production database, real SMS, refund or AI
service is used. `release_gate.json` remains unchanged and rejected.

## Discovery and change

The existing club used `club_members.phone` as its unique identity. Joining with
a chosen PIN immediately issued `club_token`; paid-order points were attached by
phone. There is no separate club-number source. The implementation therefore
continues to use normalized Iranian mobile numbers and introduces no `club_no`.

`clubOwnershipService.js` creates `club_claims` bound to a signed, scoped,
HttpOnly guest identity. Join returns 202 with a generic response and a 350ms
minimum response time, for both existing and absent phones. There is no membership
lookup in the claim-creation path. PIN is only a bcrypt-hashed panel credential;
it never establishes ownership. No member or club session is created until OTP.

OTP is sent to the claimed club mobile through the provider interface. Claim,
actor identity, purpose and challenge must match. Codes use HMAC hashes,
constant-time comparison, five-minute expiry, single use, five attempts, 60-second
resend and shared daily phone/IP limits. Mobile and club identity are the same
key, so the phone quota implements both identity limits. Endpoint IP limits also
apply. Captcha is required after three failures; a durable notification alert and
append-only audit record are created. Codes and PINs are absent from audit logs.

Verification locks the mobile and rechecks the current claim. Database partial
unique indexes enforce one verified claim per mobile and one pending claim per
mobile/actor. Ownership disputes return 409 after OTP and preserve the incumbent
owner, with an invoice/card/in-person support path. No claimant receives the
incumbent's points. Proof constraints reject null or mismatched verified mobiles.

`club_point_accruals` stores unique source/order or review accruals in pending.
Release rechecks the actual source mobile against `verified_phone`, paid order or
approved review state, and creates one immutable ledger entry. A different mobile
stays pending even if bound to a verified member. Redemption checks verified
ownership again inside the transaction and shares the mobile lock with accrual,
verification and clawback. Existing conditional balance/stock writes and request
idempotency remain in place.

`POST /api/public/club/points/:id/clawback` requires ADMIN/MANAGER authentication
and a reason. It records a negative adjustment and actor/reason audit, never
deletes history, and is idempotent. Insufficient unspent points require manual
review rather than a negative balance. Both the ledger and security audit reject
UPDATE/DELETE through database triggers. DB owner/DDL rights remain privileged.

The website now requests an OTP after join, verifies before opening the account,
supports resend with a timer, displays pending points and legacy ledger labels,
and offers mobile verification for legacy accounts. No mock code or bypass is
exposed by the UI or an HTTP endpoint.

## Migration and operations

`20261020020000_verified_club_phone` marks existing accounts and ledger entries
`legacy_unverified`. Balances move to `legacy_points`; history remains intact.
Existing sessions are invalidated with `tokenVersion`. A 30-day deadline permits
new pending accrual while blocking redemption; after the deadline accrual is
read-only too. Successful OTP restores the historical balance once using a new
release adjustment, then releases matching pending sources.

The migration queues one re-verification SMS notification per member in the
existing outbox. It does not send SMS during migration. Outbox remains dry-run by
default, adapters disabled by default, with explicit non-production mocks only.
Provider delivery must honor the outbox idempotency key. The authenticated stock
metrics endpoint also exposes disputed claims, pending club points and pending
OTP alerts; these feed its alarm signal.

The migration was applied only to disposable random schemas in
localhost:55439/elin_audit. The regression fixture also deploys the actual prior
migrations, inserts a legacy account/ledger, then applies this migration. Production
schema drift, backup/recovery and historical-balance accuracy require separate
review before deployment. Baseline historical balances are preserved; deciding
whether old earnings were fraudulent still needs independent review/clawback.

## Validation

Primary evidence is in `audit/evidence/`; review copies are in
`docs/evidence/sec006/`. `open-risks.json` records the pre-change exploit:
unverified join issued a session and received order points. `sec006-after.json`
records the post-change security scenarios. `sec006-regression.log` is the full
backend test run, including SEC-005 concurrency, payments and existing club flows.
Typecheck, lint, build and read-only synthetic UI evidence are recorded separately.
All tests use mocks, isolated PostgreSQL and blocked external HTTP by default.

Remaining release requirements: implement and independently verify real SMS,
captcha and notification adapters; resolve ownership disputes operationally;
validate target database permissions/migration history; configure monitoring and
proxy trust. A passing local test run is not independent verification or approval
to deploy. No remote was supplied, so the branches and commits are local; real
pull requests can be opened after a remote is provided.
